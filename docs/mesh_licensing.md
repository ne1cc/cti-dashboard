# MeSH Condition Ontology & Licensing Record (Issue #68)

## 1. Overview & Evaluation of Condition Lookup Services

To support consumer-friendly condition search in the patient finder (e.g. mapping "sugar diabetes" to "Diabetes Mellitus", "heart attack" to "Myocardial Infarction", "memory loss" to "Alzheimer Disease"), two architectures were evaluated:

### Architecture Options Evaluated

1. **Runtime Third-Party Lookups (NLM MeSH API / ClinicalTrials.gov v2 API):**
   - *Pros:* Always reflects upstream changes without local rebuilds.
   - *Cons:* Violates local-first architecture; introduces external network dependency and variable latency (100–500ms per keystroke); risks rate-limiting; leaks patient search queries to third-party endpoints.
   - *Decision:* **Rejected** per ADR local-first design and Issue #68 out-of-scope constraint ("Runtime calls to third-party services are out").

2. **Local MeSH Condition Extract (`src/api/resources/mesh_conditions.json`):**
   - *Pros:* Sub-millisecond autocomplete query response (< 2ms); strictly zero network calls; hermetic offline operation; privacy-preserving (no patient search queries sent over the network); version-controlled and reproducible.
   - *Cons:* Requires static ontology snapshot packaged with the application.
   - *Decision:* **Chosen**. Packages canonical MeSH disease descriptors, tree hierarchies (Category C and F03), entry terms, and consumer phrases directly in the service.

## 3. Hierarchy & Ancestor Closure Integration

MeSH conditions maintain explicit hierarchical tree numbers (e.g. `C18.452.394.750` for Diabetes Mellitus).
- Selecting a parent concept (e.g., "Diabetes Mellitus") queries `stg_trial_condition_mesh` and `bridge_trial_condition`.
- Via the ancestor closure established in Issue #52, every descendant trial record (e.g., Type 1 or Type 2 Diabetes) carries closure edges (`is_ancestor = true`) for its parent nodes.
- Thus, selecting any parent concept automatically matches all descendant trials without per-disease hardcoded logic.
